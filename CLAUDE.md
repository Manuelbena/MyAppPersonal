# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Syncro is a native Android app (Kotlin, Jetpack Compose) that unifies tasks, calendar events, and notes into a single timeline, with two-way sync against a user's Google account (Calendar and Tasks APIs). UI strings and comments in the codebase are in Spanish; keep that convention when touching existing screens.

## Build, lint, and test commands

Windows shell (this repo is developed on Windows) — use `gradlew.bat` when running outside Git Bash, or `./gradlew` inside it.

```
./gradlew assembleDebug              # build debug APK
./gradlew installDebug                # build and install on connected device/emulator
./gradlew test                        # run JVM unit tests (app/src/test)
./gradlew testDebugUnitTest --tests "com.syncro.data.repository.TaskRepositoryImplTest"   # run a single unit test class
./gradlew connectedAndroidTest        # run instrumented tests (app/src/androidTest), needs a device/emulator
./gradlew lint                        # Android Lint
```

There is no ktlint/detekt config in this repo — Android Lint is the only configured static check.

### Tests

JVM unit tests in `app/src/test` run on Robolectric (`src/test/resources/robolectric.properties`: SDK 35, plain `Application` so Hilt/SyncroApp don't start) against a **real in-memory Room DB** (`testutil/TestData.kt`: `createInMemoryDatabase()`, fixed `DAY` date, `aTask`/`anEvent`/`aNote`/`aSynced*Entity` builders). Don't mock DAOs: most data-layer bugs so far were in SQL behavior (REPLACE cascades, pending counters). Each repository test class opens with a KDoc test plan (responsibilities + risks); bug fixes get a regression test commented `// Regresión: …`. `GoogleSyncRepositoryImplTest` covers the sync logic against `testutil/FakeGoogleRemoteDataSource` (in-memory Google Tasks/Calendar with PATCH semantics, 404s and simulated network errors) plus a fixed `Clock`; `data/local/dao/SyncContractTest` pins the DAO queries it relies on. `architecture/PresentationLayerDependenciesTest` forbids presentation from importing repositories or Room (`data.auth` and `data.preferences` are allowed). Domain use cases are tested as plain JUnit (no Robolectric) with in-memory fakes in `testutil/Fakes.kt`; fakes share a `CallLog` so tests can assert ordering (local write before Google push). ViewModels are tested with the domain fakes plus `testutil/MainDispatcherRule` (swaps `Dispatchers.Main`); collect one-shot effects/StateFlows in `backgroundScope`. Compose UI is tested on Robolectric with `createComposeRule` (see `presentation/event/AddEventContentTest`), finding nodes by the text the user sees. `ExampleInstrumentedTest` in `androidTest` is still a placeholder.

## Architecture

Standard Clean Architecture layering under `app/src/main/java/com/syncro/`:

- **`domain/`** — pure Kotlin: no Android or Compose imports (enforced by `architecture/DomainLayerDependenciesTest`; its `knownExceptions` list is empty — keep it that way). Colors are `ArgbColor` (value class over the ARGB Int Room stores); `Priority` is a plain enum. Conversion to Compose `Color` and priority label/color live in `presentation/theme/ColorMapping.kt` (`toColor()`, `toArgbColor()`, `Priority.label`, `Priority.color`).
  - `model/SyncroItem.kt` defines the app's core sealed type: `SyncroItem` is `Event`, `Task`, or `Note`. Most of the UI operates on `SyncroItem`, not on Room entities directly.
  - `repository/` — interfaces only (`TaskRepository`, `EventRepository`, `NoteRepository`, `UserRepository`, `GoogleSyncRepository`).
  - `usecase/` — one class per operation (e.g. `SaveEventUseCase`, `SyncGoogleCalendarUseCase`, `ToggleTaskCompletionUseCase`). Use cases are the only things ViewModels call; they compose repositories and are the natural place for cross-cutting logic like "save locally, then push to Google."
  - Times are `LocalTime` in the domain (Room stores "HH:mm"; convert only in `data/local/StoredTime.kt`). "Now" comes from an injected `java.time.Clock` (provided in `AppModule`), never `LocalDateTime.now()` in use cases, so tests use `Clock.fixed`.
  - User-entered text in events/tasks (title, description, location, subtasks) is normalized with `String.toSentenceCase()` (`model/TextRules.kt`) in the save use cases; the form keyboards also use `KeyboardCapitalization.Sentences`, but the use case is the guarantee.
  - IDs for new tasks/events/notes are generated in the save use cases (UUID); repositories `require` a non-blank id and never invent one. Validation rules live in `model/Validation.kt` and use cases return `Result.failure` (never throw) for invalid input, so the UI can show the message.
- **`data/`** — implementations.
  - `local/dao/` + `local/entity/` — Room DAOs/entities, wired together in `local/SyncroDatabase.kt` (version-bumped manually). Migrations live in `local/Migrations.kt` and are registered in `AppModule` via `addMigrations`; they are tested in `data/local/MigrationTest` by building the previous schema from frozen fixtures (`test/.../data/local/Schema9.kt`, `Schema10.kt`, copied from the generated `SyncroDatabase_Impl.createAllTables` *before* bumping the version) and opening it with Room without destructive fallback. When bumping the version again: first freeze the current schema as a new `SchemaN` fixture, then add the migration and a test. `fallbackToDestructiveMigration` is still on, so any schema bump without a matching migration wipes local data (including unsynced items) — always add a migration when changing an entity.
  - `repository/*Impl.kt` — implement the domain repository interfaces, map between Room entities and `SyncroItem`/domain models.
  - `repository/GoogleSyncRepositoryImpl.kt` — all sync logic (download, conflict rules, deletions, push). It never touches HTTP directly: `remote/GoogleRemoteDataSource` is the transport boundary (real impl `GoogleApiRemoteDataSource`: credentials, pagination) and `sync/SyncScheduler` the retry boundary (real impl `WorkManagerSyncScheduler`), so both are faked in tests. Keep new sync logic in the repository, not in the data source.
  - `remote/GeminiApi.kt` is an unimplemented stub for a planned AI assistant feature (the Assistant chat currently only handles quick replies; see "Assistant chat").
- **`di/AppModule.kt`** — single Hilt module (`SingletonComponent`), provides the Room DB, DAOs, and repository bindings. Add new repository/DAO providers here rather than creating additional modules unless there's a real scoping reason.
- **`presentation/`** — one package per screen (`home`, `calendar`, `event`, `notes`, `login`, `assistant`), each typically with a `XyzScreen.kt` (Compose UI) and `XyzViewModel.kt` (`@HiltViewModel`, exposes `StateFlow`/Compose state, calls use cases). Shared widgets live in `presentation/components/` and per-feature subcomponents in `presentation/<feature>/components/`.
  - `presentation/navigation/` — `Navigation.kt` defines the sealed `AppScreen` route list; `MainScaffold.kt` hosts the `NavHost` plus the floating bottom nav (`FloatingBottomNav.kt`).
  - Tapping an event/task card (Home timeline and Calendar day) opens a detail bottom sheet (`event/EventDetailSheet`, `task/TaskDetailSheet`) built from the shared pieces in `components/DetailComponents.kt` (header with the item-colored gradient, pills, cards). Sheets use `dragHandle = null` and draw the handle inside the header so the gradient reaches the top edge; screens keep the selected item's *id* and look it up in UI state so the sheet reflects live changes. Category icons come from `components/categoryIcon()`.
  - Fonts are bundled in `res/font` (offline-first, no downloadable fonts): Plus Jakarta Sans for the whole UI via `Typography` in `theme/Type.kt`, and `NotebookFontFamily` (Fraunces italic) for the notebook/quote touches — use it instead of `FontFamily.Serif`. OFL licenses live in `assets/licenses`.
  - `presentation/theme/` holds the theme (`SyncroTheme`), colors and `ColorMapping.kt`.
  - Session: `AuthViewModel.session` is `SessionState.Loading | LoggedOut | LoggedIn`; `MainScaffold` renders nothing while `Loading` (avoids flashing the login) and picks the start destination once.
  - Unfinished sections use `components/ComingSoonScreen` instead of blank screens (none right now). The "+" of Home, Calendar and Savings is `components/AddFab`, and it opens an `AddOptionsSheet` (`home/components/AddItemBottomSheet.kt`) built from `AddOptionItem`s; Savings offers "Nuevo ingreso / Nuevo gasto" there (see "Savings" below). Don't ship controls that do nothing: hide them until implemented.
- Google sign-in is split: `data/auth/GoogleSignInClient` shows the Credential Manager account picker (needs an Activity `Context`) and returns a `User`; `SignInWithGoogleUseCase(account)` validates and saves it. `LoginViewModel` is the one ViewModel that calls a non-use-case class directly, because the picker is system UI.
- Dependency injection is Hilt throughout: `SyncroApp` is `@HiltAndroidApp`, `MainActivity` is `@AndroidEntryPoint`, ViewModels use `@HiltViewModel` + `@Inject constructor`.

### Sync model

Events can span days: `date` is the start day and `endDate` the end day (same day unless the event crosses midnight). The rule for which days an event is shown on is `SyncroItem.Event.occursOn` / `.days` in the domain (an event ending exactly at 00:00 does not show on its end day); DAO day/range queries return a superset and callers filter with it. All-day events are 00:00–00:00 spanning `date..endDate` inclusive (Google's end date is exclusive, converted on sync). Tasks have no separate flag: a task at 00:00 is "todo el día" (`SyncroItem.Task.isAllDay`), which is also how Google Tasks arrive since Google stores no time. New tasks are day-only: `QuickTaskSheet` (built like the event form, reusing its `internal` pieces) asks only for the day (tasks have no category), and the ViewModels always save at 00:00. In Home, the day's tasks are grouped in `TasksCard` (same style as `FocusCard`) above the events timeline; the timeline and its "Ahora" line only show events. Both the Home timeline and each Calendar day use `domain/model/DayOrdering.kt` (`sortedForDay`): all-day items first, then events continuing from the previous day, then by start time. In the Calendar grid, a day with an all-day *event* gets a colored border around the whole day cell (event chips themselves look normal); tasks always use their own style (check circle, soft fill, strikethrough when done) so they are never mistaken for events.

Offline-first. Room is the UI's source of truth; tasks/events carry a nullable `remoteId` (Google id) and a `pendingChanges` counter. Every local write (create/edit/toggle) increments `pendingChanges` in the DAO/repository, then the use case calls `GoogleSyncRepository.pushTask`/`pushEvent`, which read the *local* state and insert or patch in Google. `markSynced` only zeroes the counter if it didn't change during the upload. A failed push schedules `data/sync/PushPendingChangesWorker` (WorkManager, network constraint, `KEEP`), which calls `pushPendingChanges()` for everything pending on any date. Downloads (`syncTasks`, `syncCalendar(range)`) never overwrite or delete items with pending changes (local wins), and delete local items whose `remoteId` disappeared from Google. If a push gets 404/410 the Google deletion wins and the local item is removed. Subtask state is stored in the Google event description (`Subtareas:` + `- [x]`/`- [ ]`); Google Tasks stores no time, so local task time is kept. A task's due date is only sent to Google on insert or when `TaskEntity.dateChanged` is set (by `TaskDao.moveTask`, cleared by `markSynced` together with the counter): otherwise a patch would add a due date to Google tasks that have none (they show locally on "today"). Deleting an event or task (`DeleteEventUseCase`, `DeleteTaskUseCase`) is a tombstone: `markEventDeleted`/`markTaskDeleted` set `isDeleted` and bump `pendingChanges`, every UI query filters `isDeleted = 0` (and repositories return null by id), and `pushEvent`/`pushTask` delete it in Google (404/410 is fine) and then remove the row; never-uploaded items are removed directly. Because the tombstone is pending, a download cannot bring it back while offline. Both detail sheets use `components/DeleteItemButton` (confirmation, warns when it is also deleted in Google).

### Daily digest notifications

Local notifications in the morning and evening (`DigestMoment`, defaults 9:00 and 21:00; the user can turn each off or change its time in Settings, `DigestSettings`), built only from Room so they work offline. Domain: `GetDailyDigestUseCase` gathers today/tomorrow and the user's first name (null without a session → no notification); `DigestMessages.kt` (`DailyDigest.toMessage()`) writes the friendly text — several phrasings per situation, picked by `date.dayOfYear` so they're stable within a day and testable. Data (`data/notifications/`): `DigestAlarmScheduler` uses AlarmManager exact alarms (`USE_EXACT_ALARM`, allowed for calendar apps; falls back to `setWindow`) because WorkManager can delay hours in Doze; each alarm reschedules the next one when it fires, `DigestRescheduleReceiver` restores them after reboot/app update/time change, and `SyncroApp.onCreate` observes the digest settings and reschedules (idempotent) on every change; a disabled moment has its alarm cancelled. The evening time also marks the end of the day for the assistant (leftover review starts, priorities stop being asked). Receivers reach Hilt through `DigestEntryPoint` (same pattern as `PushPendingChangesWorker`). The POST_NOTIFICATIONS permission (Android 13+) is requested from the Assistant chat (see below).

### Settings

`presentation/settings/` (route `AppScreen.Settings`, opened from the avatar in Home's header; slides in like the notebook and hides the bottom bar). The main page is the profile card plus a list of category buttons (`SettingsPage`, each showing its current state); each opens its own sub-page inside the same screen (`AnimatedContent`, the back arrow and system back return to the list). Pages: account (logout), notifications (a switch: on requests the permission while Android still shows the dialog, otherwise opens the system settings; off opens the system settings since an app cannot revoke it — shared with the chat in `components/NotificationPermission.kt`), "Resumen del día" (morning/evening switches and times; `UpdateSettingsUseCase` rejects a morning time not before the evening one), assistant switches (`AssistantSettings`: priorities, leftover review — gated in `AssistantViewModel` and in the digest via `DailyDigest.offerFocus`/`offerLeftovers`), theme (`ThemeMode` SYSTEM/LIGHT/DARK in `ThemePreferences`, migrating the old dark boolean) and about (version, font licenses). Logic settings live behind `domain/repository/SettingsRepository` (DataStore `app_settings`); theme stays in `data.preferences` because it is UI-only. Logout (`LogoutUseCase`) first clears account data (`AccountDataRepository`: Room `clearAllTables`, assistant chat, priorities; settings and theme are kept) and then the session; `MainScaffold` then navigates to Login. Before that the dialog shows `DataLossSummary`: unsynced task/event changes and notes, which are local-only and would be lost.

### Home screen widget

`presentation/widget/TodayWidget.kt` ("Tu día", Jetpack Glance): what is left today (`domain/model/TodayAgenda.kt`: unfinished tasks, events not completed and not yet ended, in `sortedForDay` order), with a "+" that opens the app on the quick task sheet (`MainActivity.EXTRA_ADD_TASK` → `MainScaffold(addTask)` → `HomeScreen(openQuickTask)`). Data comes from `GetTodayAgendaUseCase` through `TodayWidgetEntryPoint` (Room only, works offline). Refresh: `TodayWidgetUpdater` (started in `SyncroApp`) redraws on any change to today's items, on day change and every quarter hour while the process lives; otherwise `updatePeriodMillis` (30 min, the Android minimum) in `res/xml/today_widget_info.xml`. Widgets cannot use bundled fonts (RemoteViews), so it uses the system font; colors come from the app's `LightColorScheme`/`DarkColorScheme` following the system theme. Content is tested with `glance-appwidget-testing` (`TodayWidgetContentTest`).

### Savings (Ahorros)

Income and expenses the user types in, local only (Room table `movements`, never synced, no bank connection), euros only. Domain `model/Movement.kt`: amounts are `Long` cents (never Double), `MovementCategory` per `MovementType` with a final "Otros" each (`MovementCategory.other(type)`; unknown stored names map there), `parseEuroCents` for typed input. A movement with `repeatsMonthly` is a single row that counts every month from its date (`Movement.dateIn(month)`, day clamped to the month's last day, e.g. 31 → 30 April); it is never copied, so deleting it removes it from every month. `MovementDao.observeForRange` returns a superset (month rows + monthly rows started before) and `monthMovements` filters and totals (income, expense, balance, `savingsRatePercent`). Presentation (`presentation/savings/`): `SavingsViewModel` (month from the injected `Clock`), `SavingsContent` (fixed header with the month switcher; below it the list scrolls with the shared `components/EdgeFades` like Home: summary card, rows grouped by day, future occurrences shown as "Previsto"; tapping a row opens `MovementDetailSheet` with Editar, Compartir and delete), `MovementSheet`/`MovementContent` form (new, or prefilled with `initial` to edit: `SaveMovementUseCase(id = …)` keeps the id); tickets are shared as receipt-style PNGs: `Ticket.kt` holds the generic `TicketContent` (title, `TicketBlock`s: Row/Heading/Rule/Total, footer), `renderTicket` (Canvas, monospace, torn edges, height follows content) and `shareTicket` (writes to `cacheDir/tickets`, the only path exposed by the `FileProvider` in `res/xml/file_paths.xml`, and opens the share sheet with a caption); `MovementTicket.kt` builds the content (pure, tested): `movementTicket` for one movement (detail "Compartir") and `monthStatement` for the month (button "Compartir resumen del mes" on the summary card: totals, balance, savings rate, `MonthMovements.totalsByCategory` breakdown with %, every movement by date, upcoming ones marked "*"); labels/icons/colors and `formatEuros` (NBSP before €) in `MovementUi.kt`. Movements count in `DataLossSummary` (logout warning) and are covered by the privacy policy and terms.
Budgets (`domain/model/Budget.kt`): a monthly spending limit per expense category (Room table `budgets`, PK = category name, migration 14→15, local only), managed with `Get/Save/DeleteBudgetUseCase` (income categories and 0 € are rejected). `MonthMovements.budgetStatuses` compares the month's expenses (including upcoming ones: they are committed) with each limit: `BudgetLevel` OK / WARNING from `BUDGET_WARNING_PERCENT` (80) / EXCEEDED above 100 %. `budgetAlerts(budgets, today)` walks the expenses by date and returns the day each threshold was crossed (one EXCEEDED alert only if a single expense jumps past 100 %; upcoming expenses never alert); `AssistantViewModel` turns those within the history window into chat messages (`AssistantSettings.budgetAlertsEnabled`, on by default). UI: `savings/Budgets.kt` (`BudgetsCard` under the summary card, `BudgetSheet` to create/change/remove). The month statement and its caption include budgets. Category `label` and `emoji` live in the domain (`MovementLabels.kt`) because assistant texts use them; icons and colors stay in `MovementUi.kt`.

### Legal

`presentation/legal/LegalDocuments.kt` holds the privacy policy, terms of use, legal notice (LSSI) and open-source notices, written from what the code actually does (only Google receives data; no own server, analytics or ads; Limited Use clause for the Calendar/Tasks scopes). **Any change to data handling (new server, analytics, Gemini, new Google scope, backup rules) must update the privacy policy and `LegalInfo.LAST_UPDATED` in the same change.** Owner data (`LegalInfo`) must be filled before publishing (`isComplete`). Every `openSourceComponents` entry must point to a license text bundled in `assets/licenses` (checked by `LegalDocumentsTest`); add new third-party libraries there. Documents open at route `legal/{doc}` (`legalRoute`) from Settings > Privacidad y legal and from the login footer.

### Assistant chat

The Assistant tab is a WhatsApp-style chat (`presentation/assistant/AssistantScreen.kt`, `AssistantChatContent`) with quick-reply buttons instead of a text box (free-form chat with Gemini is still to come). The conversation is not a stored log: `domain/model/AssistantChat.kt` (`assistantConversation(...)`) derives it from the user's digest answer, whether Android allows notifications, the current leftover tasks and the stored leftover decisions, so it always reflects reality (e.g. notifications re-enabled from system settings, a task completed from Home). Each message has a stable id and carries its own `options` (shown under it only while unanswered, hidden on tap) and optionally a task list. `data/preferences/AssistantPreferences` stores the digest answer, leftover outcomes, and read/cleared ids; `AssistantConversation.unreadCount` feeds the number badge on the Assistant tab (`FloatingBottomNav(badges = …)`). `MainScaffold` owns the single `AssistantViewModel` (shared with the screen so badge and chat never diverge) and `TrackAssistantOnResume` re-checks the permission and the leftovers on every resume. Opening the chat marks everything on screen as read.

Leftover tasks (`domain/model/Leftovers.kt`): before 21:00 the unfinished tasks from previous days are proposed "a hoy"; from 21:00 today's are included and proposed "a mañana". A review is identified by `reviewDate` (the night review and the next morning's are the same one, so an unanswered night review is asked again in the morning, and an answered one is not). Options: move all (`MoveTasksUseCase`, keeps the time), one by one (per-task: target day / other day with a date picker limited to ≥ the target / done), or keep. The outcome is saved *before* moving so the question never flickers away. Reviews from the last 7 days stay in the chat. Daily priorities (`domain/model/DailyFocus.kt`): before 21:00, if today has ≥ 2 unfinished tasks and no unanswered leftover review, the chat asks for up to 3 priorities (`ChatMessage.maxSelectable`, star toggles; `ChatReply.FOCUS_CONFIRM` carries the selected ids, `FOCUS_SKIP` = "Hoy no", stored as an empty list so it isn't asked again). Chat blocks are ordered chronologically: a review of day D goes after D's priorities and before D+1's. Priorities are local only (`DailyFocusRepository`, DataStore `daily_focus`, one key per day with the task titles snapshotted for the chat); `GetDailyFocusUseCase` resolves them against current tasks (keeps done ones, drops tasks moved to another day) for Home's `FocusCard` above the timeline. The morning notification invites choosing them (`DailyDigest.offerFocus`). "21:00" above means the configured evening time.

The 21:00 notification with pending tasks (and the 9:00 one inviting to choose priorities) sets `DigestMessage.opensAssistant`; `MainActivity` reads `DigestNotifier.EXTRA_OPEN_ASSISTANT` and `MainScaffold(openAssistant = …)` navigates to the chat. The header's clear button (with confirmation) stores the current ids as cleared (`clearedIds`); messages with new ids still appear later. The chat uses only `MaterialTheme.typography` styles and the same header layout as Home (no hardcoded `sp`). To add a new assistant message, add it to `assistantConversation` with a new id: it shows up unread automatically.

Payday (`domain/model/Payday.kt`): `AssistantSettings.paydayDay` (1–31, clamped to the month's last day; **null by default** = no salary, nothing is said), set in Settings > Asistente > "Día de nómina" (`PaydayDialog`, "No tengo nómina" or a day). `AssistantViewModel` builds a `Payday` for `lastPayday(...)` if it was within the chat history window, with `MonthMovements.salaryCents()` (income in category Nómina that month) and the stored `PaydayAnswer` (`AssistantPreferences.paydayAnswers`, key `payday_DATE`). The chat greets with a banking tip and asks to register the salary (`ChatReply.PAYDAY_REGISTER` also calls `onRegisterSalary`, which `MainScaffold` turns into navigating to Savings with `openSalaryForm` → income form with `presetCategory = SALARY`); once a salary is recorded it shows the 50/30/20 split (`salaryPlan`, exact cents). On payday the morning digest (`DailyDigest.isPayday`) announces it and opens the chat. Shared captions (`movementShareText`, `monthShareText`) use WhatsApp formatting (`*bold*`, `_italic_`), `///` headers and `MovementCategory.emoji`.
